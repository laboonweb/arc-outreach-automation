## Proposed isolation and hard limits

Approval of this plan would authorize **staging creation and synthetic Cloud writes only**, never publication, deployment or changes to existing workflows/tables.

- Create four new Data Tables, copying the exact current schemas: synthetic Review Queue, Protection Ledger, Inbox and Links. Names share one unique `Arc Operator Smoke <run-id>` prefix. Do not reuse the existing Synthetic Claim Validation table.
- Create four new **inactive/unpublished** workflows: full candidate panel clone, candidate handoff clone with a Code response mock in place of provider HTTP, candidate Inbox Sync clone, and a bounded seed/assertion/control harness. Existing five engines and panel stay version-unchanged.
- Use eight allowlisted synthetic queue records, eight corresponding Inbox records, eight links and two synthetic protection entries: **26 initial row inserts at most**. No extra records on retries. Contacts use reserved example domains; social URLs are fixture strings and are never visited.
- Use a separate random staging signing key, existing Basic Auth credential reference, staging-only absolute `/webhook-test/` paths and a visible synthetic banner. Never print/export credential values into the report or browser.
- Replace panel/handoff source HTTP reads with deterministic Code fixture responses in the exact expected Sheets shapes, including registry/ID/row association. Keep business eligibility, token, CAS, projection, copy, claim and receipt logic unchanged. Static inspection must find no production table IDs, production sub-workflow references, real provider connection or callable research/provider/send endpoint in these three synthetic execution graphs.
- The fourth control harness has a separate, explicit, read-only integrity branch limited to the three configured Google workbooks. Before/after, read values, formulas and relevant effective formats/theme/row associations one workbook at a time, hash them, and return only compact receipts. At most **six Google Sheets GETs total**. No general evidence fetch, sheet write, research run or provider access. If complete value/formula/format proof cannot be obtained, report that gap and stop the release gate.
- **84 Cloud executions maximum, including children:** at most 60 panel requests (16 GET + 44 POST), 8 control/harness executions (including seeding and both integrity checks), 6 mocked handoff executions, and 10 sync executions. At most six additional deliberately denied authentication requests; if any creates an execution, it consumes the same 84-run budget. Arm test listeners only for the next request. Use manual execution intent, never production execution mode. No schedule, activation or publish call.
- **500 matched/attempted synthetic row mutations maximum**, including initialization, updates, no-op upserts and fault recovery; the same 26 identities remain the maximum row count. Reserve the next execution's maximum possible writes before starting it; do not begin a run that could exceed the remaining budget. Count native node items and verify actual table counts after each stage. Typical writes are lower; this cap includes projection/recovery amplification.
- **5 MiB maximum staging table data**, measured as serialized UTF-8 application data plus reserved headroom. This is a conservative test budget, not a proof of n8n physical storage consumption. Check actual account usage/quota before creation; stop if unknown/insufficient or within the warning threshold. No quota-exhaustion or load test.
- Single execution at a time. No automatic retry. Any isolation failure, production diff, unaccounted provider/network node, partial write, ambiguous result or unexpected cost stops the next stage.

The test harness/clone adapter artifacts will be constructed and inspected after approval, with a manifest of actual returned IDs, exact node differences, fixture IDs and budgets before execution. A tool/import/test-listener limitation does not authorize publishing a test workflow or editing a live workflow as a workaround. Changes to the approved scope require a revised approval.

## Rollback and recovery

### Before the approved smoke test

Export fresh versions, published-version metadata, schemas and all four production tables, with hashes and counts. Compare against this preflight; unexplained drift stops setup. Keep all exports private. Record current source integrity hashes and the actual returned staging IDs. The immutable original workflow baselines are `private/operator-lifecycle/{panel,draft,review,zoho,sync,copy}-before.json`; preserve them. Capture fresh data at every future maintenance window; workflow baselines are not current queue backups.

### If the isolated smoke test fails

1. Stop test listeners and further runs. The live panel and five original engines need no rollback because none was changed.
2. Export current synthetic Queue/Inbox/Links/protections and compact execution/node receipts, preserving any CLAIMED/UNKNOWN result and audit. Record the failure stage, expected payload/hash and observed stored payload/hash.
3. For a persistence failure, determine whether the canonical CAS update committed. If it did, preserve that record and repair only the projection using the tested sync path. If it did not, obtain a fresh token before any allowed resubmission. Never retry the old signed request blindly. A conflicting Inbox command/association requires explicit reconciliation.
4. For a provider-mock receipt failure, retain the claim, recover the captured mock receipt and verify draft key/message hash/claim timestamp/execution before conditional persistence. Never call the mock again as a substitute for reconciliation. No production claim/provider receipt is changed.
5. Recheck all production table/source hashes and workflow versions. Any unexplained production change stops the investigation and cannot be undone without the owner's explicit authorization.
6. Archive only the four new test workflow drafts after saving proof. Retain labelled synthetic tables; deleting them requires a separate reviewed cleanup scope. Failed smoke does not authorize production deployment.

### Future production rollback, only if deployment is separately approved

The deployment approval should explicitly cover a maintenance freeze, panel deactivation if needed, restoration of the six saved workflow baselines and republishing the original panel only when data compatibility is proven. It never authorizes deleting history or resetting provider locks.

1. Stop operator writes and all manual Phase 2 runs. If safe read-only operation cannot be established immediately, deactivate the panel rather than leave a partially restored write path available. Record active executions and inspect completion; do not interrupt an in-flight real provider request and then assume it did nothing.
2. Export the latest canonical queue, projections, protections, current workflow draft/active versions and execution/receipt evidence before any restoration. Preserve all post-release observations, copy, audit, suppression, replies, SENT timestamps, claims and provider IDs.
3. Restore baseline node parameters/graph/settings using saved workflow versions or the exact private JSON, checking every returned version and credential reference. Restoring a draft is not proof that the active panel was restored; published-version verification is separate. All five engines remain inactive/manual.
4. **Do not restore whole production tables from the old 17-row backup, or from any older snapshot over newer legitimate events.** No source/Arc Research rollback is needed because this extension never writes them. Correct only a demonstrated corrupt field/association using exact-current comparisons, owner authorization and a correction audit; never erase a suppression, contact history or provider claim to make old code work.
5. Old baseline code predates operator_workspace/request checks. If any new operator records exist, keep the write paths frozen until their safe handling is established; do not blindly reopen the old panel or run the old handoff against new approvals. Prefer a locally repaired forward release with the current data preserved. A read-only maintenance surface or targeted compatibility guard needs a reviewed patch.
6. For an actual provider timeout or receipt-write loss, keep CLAIMED/UNKNOWN locked. The operator verifies the matching existing draft in Zoho using approved message, recipient, sender, timestamp and captured response. A confirmed ID can be reconciled only to its exact claim, with audit and conditional persistence, under separate explicit authorization. Uncertainty remains locked. No new CREATE_DRAFT, reset, deletion or send is a recovery step.
7. Reopen only after exact provider/history/protection invariants and fresh projections/auth/version checks pass; report any unavailable operations and retained data. Rollback does not silently discard the operator's work.
